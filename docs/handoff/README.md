## 먼저 읽을 내용

PayloadLab은 내 입력이 문장/요청에 들어가 어떤 비교·처리를 거쳐 결과를 만드는지 관찰하는 교육용 프로젝트다. SQL은 메모리 SQLite에서 실행한다. SSRF·CMDi·Linux·권한은 모형을 사용한다. XSS는 태그 인식과 실제 브라우저 미리보기 실행을 구분한다.

| --- | --- | --- | --- |
| #19 | 입력→조립 문장→비교/처리→결과→다음 관찰을 연결해 “왜 이런 결과인가”를 설명 | 문안·trace·학습 안내·터미널 보완, 대표 검사 근거 있음. 팀 최종 검토/반영 판단은 별도 | [#19 수정 이유와 방식](issue-19.md) |

#19는 결과의 의미, #42는 요청 하나의 처리량, #44는 모이는 요청의 양과 실행 자리를 다룬다. 따라서 자원 제한/요청 거부를 #19의 “조건이 거짓이라0행” 설명으로 바꾸면 안 된다.

## 읽는 순서

1. 해당 이슈 문서의 문제·수정 의도·전후 예시를 읽는다.
2. 구현 위치 표에서 코드와 검사를 찾는다.
3. 상세 검증 문서·로그·원자료·화면을 확인한다.
4. 추가 작업 전 [WORK-STATE](../WORK-STATE.md)와 실제 Git 상태를 대조한다.

각 이슈 설명은 **문제 → 의도 → 전후 예시 → 구현 → 결정 근거 → 검증 → 한계 → 추적**을 중심으로 정리했다. 미래 작업의 설계나 숫자를 미리 확정하는 템플릿은 넣지 않았다.

## 다른 AI가 이어받을 때

- 이미 구현·검증한 기능을 요약만 보고 새로 만들지 않는다.
- app.main.app과 create_review_app, 실제 실행과 모의 출력, 자동 검사와 실제 브라우저 관찰을 구분한다.
- #42 숫자/SQL 허용 정책, #44 N·A/B·여유폭/프록시 조건은 팀 미승인이다. 정책 가상 모형 통과를 운영 용량 보장으로 쓰지 않는다.
- 태성님이 최종 검토한다. 리뷰·main 반영·종료·공개는 별도 절차다.
- 새로운 승인 범위를 추측해 정책을 활성화하거나 PR·이슈를 자동 종료하지 않는다.
