## 2. 재개·완료 기록 규칙

1. 이 문서의 1~2절 → git status/log → 현재 작업 ID의 행·계획·필요한 코드 순으로 읽는다. 예전 대화와 모든 이슈를 다시 읽지 않는다. 이 문서 전체를 매 도구 호출마다 반복해서 읽을 필요도 없다.
2. 한 작업의 **실패 테스트 작성 → 실패 확인 → 최소 구현 → 통과 확인 → 브라우저 확인(해당 시)**마다 위 체크포인트를 덮어써 저장한다. 긴 작업은 `[ ] 진행 중`으로 남기고 실제 하위 단계를 적는다.
3. 작업 완료 시 아래 `[ ]`를 `[x]`로 바꾸고 구현 커밋/테스트 근거를 그 행에 연결한다. 코드와 상태 갱신을 같은 커밋에 포함한다. 커밋 SHA의 자기참조는 만들지 말고 테스트 기록 경로와 `git log -- 해당파일`로 추적해도 된다.
4. 상태는 **미착수 / 진행 중 / 구현·자동 검사 완료, 브라우저 미검증 / 검증 완료 / 자문 대기 / 차단 / 해당 없음**으로 구분한다. 해당 없음에는 이유와 검토 근거가 필요하다.
5. 자동 검사를 통과해도 브라우저가 필요한 행은 완료로 체크하지 않는다. 반대로 브라우저 미검증 때문에 앞선 독립 순수 함수 검사까지 다시 할 필요는 없다. 코드/환경이 바뀌면 영향받는 검사만 우선 재실행한다.
6. 세션 종료·업무 전환 전에 체크포인트를 저장한다. 강제 중단 때 저장되지 않을 수 있으므로 다음 재개에서 diff/파일/최근 로그를 대조한다. 테스트 결과가 없으면 필요한 검사를 다시 실행한다.
7. 상단과 완료 근거는 짧게 유지한다. 큰 로그·스크린샷은 관련 검증 기록에 저장하고 링크만 남긴다. 체크리스트·계획 파일에 별도의 중복 진행표를 만들지 않는다.

## 3. 반드시 보존할 요구사항

- 웹 1–4: 목차 | 학습 공간. **처리 흐름·결과 위 / 간결한 입력·하단 고정 Lens 아래**. Enter 실행, Shift+Enter 줄바꿈, IME 보호, 큰 관찰 장면은 Esc→확인 Enter로 닫고 입력에 복귀한다.

- 원문 오류는 Linux 형식의 **모의 출력**이다. 문제 구절 밑줄 + hover/focus 짧은 설명 + 행 옆 해설 + 하단 Lens + 같은 근거의 ASCII/TUI를 연결한다. 권한 거부·문법·모형 미지원을 구분한다.
- CMDi는 hostname→조립 명령→모의 출력, Linux/권한은 command 입력이다. 모형이 모르는 명령을 실제 Linux에도 없다고 설명하지 않는다. 실제 셸·도구 설치·외부 요청·호스트 파일 접근은 추가하지 않는다.

- 중성 어두운 배경에서 패널·입력·Lens의 위계를 재설계하되 라이트 기능을 손상하지 않는다. 새 로고는 만들지 않고 승인된 공통 SVG를 유지한다.

## 7. 막히거나 중단됐을 때 저장할 최소 내용

```text
현재 ID / 상태 / 계획 Step:
직전에 한 일 / 변경 파일:
마지막 명령 / 실제 결과 / 증거:
현재 실패 또는 필요한 결정:
다음 한 행동 / 기대 결과:
완료로 바꾼 ID와 근거:
```

이 내용을 상단 체크포인트에 반영하면 된다. 긴 일지와 채팅 복사는 불필요하다. 완료된 과제의 상세 로그는 관련 이슈/검증 기록에 연결한다. 파일을 읽는 비용 자체가 0이 되거나 강제 종료 직전 저장이 보장되는 것은 아니다.

## 8. 필요한 때만 열 문서

- [첫 진단 스파이크 계획](superpowers/plans/2026-10-24-terminal-diagnostic-spike.md): UX-01의 테스트/최소 코드/명령. 진행 상태는 이 문서만 갱신한다.
- [A–Z 검증](verification/2026-10-24-release-checklist.md): 실제 검증 결과 양식과 통과 기준. 이번 수정 작업의 실행 순서를 대신하지 않는다.
