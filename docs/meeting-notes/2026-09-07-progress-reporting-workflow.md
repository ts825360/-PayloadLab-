# GitHub 기반 진행 보고 기준

연결 이슈: [#1 GitHub 운영 가이드](https://github.com/ts825360/-PayloadLab-/issues/1), [#3 팀 작업 흐름](https://github.com/ts825360/-PayloadLab-/issues/3)

## 목적

교수님께 매주 금요일 또는 격주 금요일에 진행 상황을 보고할 때, GitHub의 Assignee·Pull Request·Issue 상태를 같은 기준으로 읽습니다.

> 이 문서는 GitHub에 실제로 표시된 기록을 보고서로 정리하는 기준입니다. 담당자와 PR, 이슈 상태는 실제 작업 내용과 맞게 유지합니다.

## 상태를 읽는 방법

| GitHub 상태 | 보고서 분류 | 보고서에 쓰는 말 |
| --- | --- | --- |
| Assignee 있음 + Pull Request 있음 + Issue Open | 이번 기간 완료 | 작업 결과를 Pull Request로 올렸고, 검토 또는 최종 확인이 남아 있음 |
| Assignee 있음 + Pull Request 있음 + Issue Closed | 이전 완료 | 이전 기간에 끝났고, 현재는 참고·검증 대상으로 관리함 |
| Assignee 있음 + Pull Request 없음 + Issue Open | 진행 중 또는 미완료 | 담당자는 정해졌지만, 이번 기간에 제출할 결과물이 아직 없음 |
| Assignee 없음 + Issue Open | 배정 전 | 아직 담당자나 시작 시점을 정하지 않음 |
| Pull Request 있음 + Assignee 없음 | 기록 확인 필요 | 연결 이슈와 담당자를 확인해 GitHub 기록을 정리함 |

## 보고 전 확인 순서

1. 보고 기간에 생성·수정된 Pull Request를 확인합니다.
2. 각 Pull Request에 연결된 Issue와 Assignee를 확인합니다.
3. 위 표에 따라 이번 기간 완료, 이전 완료, 진행 중, 배정 전으로 나눕니다.
4. 각 항목에 결과물 링크, 한 줄 결과, 남은 문제를 적습니다.
5. 격주 수요일 토의에서 결정된 내용이 있다면 `docs/decisions/`와 이슈 댓글을 함께 확인합니다.

## 교수님 보고서 틀

```markdown
# PayloadLab 진행 보고

보고 기간: YYYY-MM-DD ~ YYYY-MM-DD

## 이번 기간 완료
| 담당자 | 이슈 | Pull Request | 한 일 | 남은 확인 |
| --- | --- | --- | --- | --- |
| 이름 | #번호 | PR 링크 | 결과를 한 문장으로 | 다음 확인 사항 |

## 이전 완료 작업
| 담당자 | 이슈 | 결과물 | 현재 활용 방식 |
| --- | --- | --- | --- |
| 이름 | #번호 | PR 또는 문서 링크 | 이번 기획·검증에서 어떻게 참고하는지 |

## 진행 중 또는 미완료
| 담당자 | 이슈 | 현재 상태 | 다음 행동 |
| --- | --- | --- | --- |
| 이름 | #번호 | 막힌 이유 또는 진행 내용 | 다음 보고 전 할 일 |

## 이번 토의에서 정한 내용
- 결정 내용
- 결정 이유
- 다음 보고 전 확인할 점
```

## 운영 순서

1. 팀원은 맡은 이슈와 Pull Request를 최신 상태로 정리합니다.
2. 격주 수요일 토의에서 열린 이슈, Pull Request, 문서를 함께 확인합니다.
3. 총괄 담당자는 위 표 기준으로 금요일 보고 초안을 만듭니다.
4. 교수님께 보고한 뒤, 새 결정이나 피드백은 Issue와 `docs/decisions/`에 남깁니다.

## 원칙

- Pull Request가 연결된 열린 이슈는 “이번 기간에 결과물을 제출하고 검토 중인 작업”으로 보고합니다.
- Issue를 닫을 때는 결과물 링크와 확인 방법을 남깁니다.
- 보고서에는 구현 여부뿐 아니라 문서화, 자료조사, 테스트, 오류 수정처럼 실제로 한 검증 작업도 적습니다.
- 기능이 이미 있어도, 그 기능을 다시 확인·개선·문서화한 내용은 현재 보고 기간의 작업으로 기록할 수 있습니다.
