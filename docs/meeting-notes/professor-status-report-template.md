# PayloadLab 교수님 상태 보고 템플릿

> 이 문서는 교수님이 한눈에 읽는 **한 장짜리 상태 보고서**입니다. GitHub 이슈·Pull Request의 상세 목록은 본문에 모두 넣지 않고, 필요한 근거 링크만 마지막에 둡니다.

## 작성 원칙

- 본문은 한 페이지 또는 5분 안에 읽을 수 있는 분량으로 작성합니다.
- 각 항목은 최대 3개 핵심 항목만 적습니다.
- “무엇을 했다”보다 “무엇이 달라졌고, 왜 중요한가”를 먼저 적습니다.
- 해결되지 않은 일은 숨기지 않고, 다음 행동이나 교수님 의견 요청을 함께 적습니다.

## 상태 표시

| 상태 | 사용할 때 |
| --- | --- |
| 🟢 정상 진행 | 현재 계획대로 진행 가능 |
| 🟡 확인 필요 | 결정·검증·의견이 더 필요함 |
| 🔴 지연 위험 | 다음 작업을 막는 문제 또는 외부 도움이 필요함 |

# PayloadLab 진행 보고

**보고 기간:** YYYY-MM-DD ~ YYYY-MM-DD  
**전체 상태:** 🟢 / 🟡 / 🔴  
**이번 기간 한 줄 요약:** 이번 기간에 무엇을 확인했고, 프로젝트에 어떤 의미가 있는지 한 문장으로 적습니다.

## 1. 이번 주에 한 일

- **[결과 1]** 무엇을 했고, 어떤 결과를 확인했는가
- **[결과 2]** 무엇을 했고, 어떤 결과를 확인했는가
- **[결과 3]** 무엇을 했고, 어떤 결과를 확인했는가

## 2. 해결되지 못한 일

| 내용 | 왜 아직 해결되지 않았는가 | 현재 영향 |
| --- | --- | --- |
| 미해결 항목 | 결정·검증·시간·자료 등 이유 | 다음 작업에 미치는 영향 |

## 3. 토의를 통해 해결된 일

| 논의 주제 | 팀의 결정 | 결정 이유 |
| --- | --- | --- |
| 예: 첫 버전 범위 | SQL·XSS·IDOR 중심 | 입문자 학습 흐름을 먼저 검증하기 위해 |

## 4. 다음 주에 할 일

- **[다음 작업 1]** 담당자와 확인할 결과
- **[다음 작업 2]** 담당자와 확인할 결과
- **[다음 작업 3]** 담당자와 확인할 결과

## 5. 남은 일

| 남은 항목 | 현재 단계 | 완료 판단 기준 |
| --- | --- | --- |
| 남은 작업 | 배정 전 / 진행 중 / 검토 중 | 무엇이 확인되면 끝나는지 |

## 6. 교수님 의견 요청

이슈 댓글과 팀 토의에서 나온 질문 중, 팀 내부에서 결정하기 어렵거나 방향 확인이 필요한 것만 적습니다.

| 관련 이슈 | 팀의 질문 | 지금까지 검토한 선택지 | 교수님께 받고 싶은 의견 |
| --- | --- | --- | --- |
| #번호 | 질문을 한 문장으로 | 선택지 A / B | 어떤 기준으로 결정하면 좋을지 |

## 근거 자료

- Issue: #번호 링크
- Pull Request: PR 링크
- 팀 문서: `docs/` 문서 링크

## 작성 후 확인

- [ ] 맨 위 한 줄만 읽어도 현재 상태를 알 수 있는가?
- [ ] 이번 주 결과와 다음 주 계획이 각각 3개 이하인가?
- [ ] 해결되지 않은 일에 이유와 다음 행동이 있는가?
- [ ] 교수님 의견 요청이 예/아니오로 끝나지 않고, 판단 기준을 묻는 질문인가?
- [ ] 상세 GitHub 기록은 근거 자료로만 연결했는가?

## 참고한 보고 방식

상태, 성과, 위험·막힘, 결정, 다음 행동, 이해관계자 요청을 짧게 정리하는 프로젝트 상태 보고 방식을 적용했습니다. [Atlassian의 프로젝트 상태 보고 안내](https://www.atlassian.com/agile/project-management/status-report)를 참고했습니다.
