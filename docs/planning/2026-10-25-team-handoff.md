## 본인 작업을 표시하는 순서

1. **맡을 작업 이슈**의 `Assignees → Assign yourself`로 본인을 지정한다. 권한이 없으면 GitHub ID와 맡을 범위를 댓글에 적어 지정 요청한다. 기존 담당자가 있으면 협의해 본인을 추가한다.
2. 시작 댓글에 **할 일·파일·완료 기준·목표일**을 적는다. 둘이 맡으면 각자의 범위를 나눈다.
3. 최신 main에서 본인 작업 브랜치를 만들고 실제 수정·검토한 내용을 **본인 GitHub 계정으로 작은 단위로 commit/push**한다. 공통 기준은 main이다.
4. 커밋/PR에 이슈 번호를 연결한다. 문서·검증 결과는 docs/에 저장해 커밋한다.
5. 결과 댓글에 **수정 내용과 이유·커밋/PR·검증 SHA/환경/방법/실제 결과·실패/미실시·남은 문제**를 적는다. 양식은 #46에 있다.
6. 실제 확인한 체크만 채운다. 검토·검증 후 main에 반영하고 완료 기준 전체를 충족했을 때 닫는다. 일부 작업 PR은 `Refs #번호`, 전체 완료 PR은 `Closes #번호`로 연결한다.

**Assignee는 누가 맡았는지, 커밋·PR·검증 문서는 무엇을 했는지를 보여준다.** 격주 수요일 토의와 교수님 보고에는 실제 작업·검증·토의 근거를 사용한다.

## 최종 공개 배포까지의 순서

1. #12에서 운영 구성, #22/#13에서 기능·UX, #24와 #42~#45에서 보안 보완·공개 판단 근거를 마련한다. 이슈가 닫혔다는 표시만으로 공개 가능하다고 판단하지 않는다.
2. #47 담당자는 호스팅·도메인·HTTPS·API 경로, 비용·운영 기간, 배포할 SHA/이미지, 상태 확인·경보, 긴급 중지/복구 방법을 제안하고 외부 공개 없는 사전 환경에서 확인한다. 실제 절차는 담당자가 `docs/deployment/public-release-runbook.md`를 새로 작성해 커밋한다.
3. 사용자에게 대상 환경·공개 URL/범위·버전·비용·운영 책임·잔여 위험·복구 방법을 제시해 **실제 공개 승인**을 받고 기록한다. 담당자 지정이나 PR 머지는 배포 승인이 아니다.
4. 승인된 버전을 배포한 뒤 공개 주소에서 프론트/API·HTTPS·학습 흐름·상태를 확인한다. 최종 URL·버전·실행 기록과 운영/복구 문서를 README/#25에 연결한다. 실제 공개·배포 후 확인·운영 인계까지 끝난 뒤 #47을 닫는다. 계획 완료·승인 대기라면 계속 열어둔다.

배포 방식·호스팅·비용은 아직 확정하지 않았다. 이번 변경은 이슈와 문서 보완이며 실제 배포·구매·외부 공개는 수행하지 않았다.

- [WORK-STATE](../WORK-STATE.md)와 [이슈 가이드](../ISSUE-GUIDE.md)를 따른다. 미완료 항목을 체크하거나 닫지 않는다.
