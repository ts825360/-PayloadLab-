# PayloadLab 역할 분담 현황

연결 이슈: [#3 팀 작업 흐름](https://github.com/ts825360/-PayloadLab-/issues/3)

> 이 문서는 역할이 확정된 뒤 총괄 담당자가 한 번에 갱신합니다. 팀원은 이 문서를 직접 수정하지 말고, [#3 팀 작업 흐름](https://github.com/ts825360/-PayloadLab-/issues/3)에 역할 댓글을 하나 남깁니다.

## 역할과 현재 반영 이름

| 역할 | 맡을 일 | 이름 (총괄 반영) |
| --- | --- | --- |
| 총괄·GitHub 운영 | GitHub 설정, 문서·이슈 흐름 관리, 회의 진행, 결과물 최종 확인 | `[이름 입력]` |
| 공격 유형 조사 | SQL Injection·XSS·IDOR 등 공격 유형의 개념, 초보자 학습 범위, 방어 개념 조사 | `[팀원 A 이름 입력]` |
| 문제 제시·DreamHack 조사 | 유형별 DreamHack 학습 문제를 찾아, 초보자가 어떤 문제를 만나고 어디에서 어려워하는지 정리 | `[송선호 ]` |
| 프런트엔드·백엔드 | 입력 화면, Lens, 다이어그램, 교육용 결과 처리 등 구현 담당 | `[팀원 C 이름 입력]` |
| 유형·문제 대조와 범위 설정 | 공격 유형 조사와 DreamHack 문제를 비교해, PayloadLab에서 다룰 범위와 제외할 범위를 정리 | `[팀원 D 이름 입력]` |

## 역할별로 남겨야 할 결과

| 역할 | 주로 남길 곳 | 결과 예시 |
| --- | --- | --- |
| 총괄·GitHub 운영 | Issue, `docs/decisions/`, `docs/meeting-notes/` | 이슈 구조, 회의 결정, 일정·진행 정리 |
| 공격 유형 조사 | `docs/research/` | 유형 설명, 초보자 학습 목표, 자료 출처 |
| 문제 제시·DreamHack 조사 | `docs/research/` | 참고 문제, 초보자가 막힐 지점, 문제 제시 방식 |
| 프런트엔드·백엔드 | Pull Request, 관련 Issue | 화면·API·교육용 시나리오 구현과 확인 결과 |
| 유형·문제 대조와 범위 설정 | `docs/decisions/`, 관련 Issue | 첫 버전에 넣을 내용과 제외할 내용 |

## 역할 댓글을 남기는 방법

각 팀원은 `#3`에 아래 형식으로 댓글을 **한 번만** 남깁니다.

```markdown
## 역할 확인
- 이름:
- GitHub ID:
- 맡을 역할:
- 역할을 이해한 내용 또는 궁금한 점:
```

## 역할을 확정하는 순서

1. 팀원 5명이 `#3`에 역할 댓글을 남깁니다.
2. 총괄 담당자가 다섯 댓글을 확인하고, 이 문서의 이름 표를 한 번에 갱신합니다.
3. 총괄 담당자가 역할과 현재 열린 이슈를 확인합니다.
4. 지금 바로 시작할 이슈만 해당 팀원에게 Assignee로 지정합니다.
5. 아직 기획 검토가 필요한 이슈는 배정하지 않고 열어 둡니다.
6. 격주 수요일 토의에서 진행 내용과 겹치는 역할을 확인하고, 필요하면 역할·이슈 연결을 조정합니다.

## 원칙

- 역할은 고정된 벽이 아닙니다. 더 좋은 방법이나 다른 근거가 있으면 누구나 이슈에서 제안할 수 있습니다.
- 한 사람이 맡은 역할과 다른 이슈에 의견을 남기는 것을 막지 않습니다.
- `#3`의 역할 댓글이 5개 모이기 전에는 실제 이슈 Assignee를 정하지 않습니다.
- 역할이나 범위가 바뀌면 이 문서와 관련 이슈 댓글을 함께 고칩니다.
