# #44 정책 2차 검증 — 산식·지연 반례·전체 상한 대조

## 2. 숫자 재계산 결과

- 프로파일1/2/4/8개 각각204건, 합계816건을 확인했다.
- 원시 응답 시간에서 중앙값·표본p95·최대값을 다시 계산해 저장된 통계와 대조했다.
- CPU 시간은 Decimal로 재계산했다. 최대 프로파일 평균은8.9613970588…ms/요청이며,13N을 곱한 CPU 계획값은 기존 표와 일치했다.
- 전체 rate13N=4N+4N+4N+N, burst4N=N+N+N+N임을 확인했다.
- 숫자 계산 오류는 찾지 못했다. 아래 가정·검증 방식2곳을 보완했다.

이 단계는 원자료 재검산이다. 실제 HTTP816건을 새로 전송한 것으로 쓰지 않는다.

## 3. 보완1 — 2N 동시 실행의 적용 가정

기존 가상 재생은 모든 보유시간을 관측 최대를 올린133ms로 두었다. 이 조건에서2N은 통과했다. 그러나 요청마다320ms 목표 이내라고 해서2N이 언제나 충분한 것은 아니었다.

정수ms 사건 모형으로 metadata 시작 뒤10회 조작을 만들었다. 각 조작은320ms 간격으로 analyze/attempt를 요청하고, **허용된 attempt가 완료된 뒤에만** render를 만든다. 거부된 attempt에 성공 미리보기를 붙이지 않았다.

| 예시 | 결과 |
| --- | --- |
| N=1, 동시2N, 각응답161ms | 실제 생성 요청26건 중21허용·5거부. 거부된 시도 때문에 미리보기5건은 생성하지 않음 |
| 같은 모형 동시3N, 각응답320ms | 생성31건 모두허용·거부0 |
| 동시3N, 각응답321ms | 이전 작업이 분류별N 자리를 아직 사용 중이어서 일부 거부. 목표를 넘은 조건에서 무제한 허용하지 않음 |

161ms 사례에서는 이전 render가 다음 analyze/attempt와 겹친다. 처음의2개 자리 가정만으로 이를 수용할 수 없었다.

N=1/4/8/16 × 동시계수2/3 × 지연6개, 총48조건을 확인했다. 이 모형에서3N은133~320ms를 통과했지만 실제 처리 용량을 검증한 것이 아니다. metadata 시작이 끝난 뒤 학습하는 가정이며 네 분류의 임의 동시 요청·추가 탭·실제 사용자 공정성을 보장하지 않는다.

이에 정책 문서는 동시 실행을 **A안2N / B안3N 미선택 비교**로 수정했다. B안이 자동 승인된 것은 아니다. 특히 N=4의 B안12동시는 실측 상단8 밖이므로 추가 실측/운영 검토 없이 선택하면 안 된다.

## 4. 보완2 — 전체 상한만의 효과를 분리

기존 초과 재생은 초기4N을 모두 사용해 전체와4개 분류 예산을 함께 소진했다. 다음 rate_limit이 전체 예산 때문인지 분류 예산 때문인지 이 사례 하나로 구분할 수 없었다.

또한 후보의 전체13N·burst4N은 분류별 합계와 같다. 현재 후보에서 더 엄격한 독립 서비스 상한이라고 표현하면 안 된다. 합계 경계로 명시한 것과 모듈이 더 낮은 전체 상한도 적용할 수 있다는 것은 별개다.

N별4개의 독립 대조를 추가했다.

1. 같은 분류 예산·같은 동시 실행·같은 시계·IP 정책으로 controller 두 개를 만든다.
2. 전체 burst만 N과4N으로 다르게 둔다.
3. analyze N건을 처리·반납한다. attempt 예산은 양쪽 모두 사용하지 않았다.
4. IP를 바꾼 attempt는 전체 burst N 쪽에서 rate_limit,4N 쪽에서는 허용된다.

따라서 전체 예산 모듈의 독립 작동은 대조로 확인했다. 기존 후보13N/4N을 더 낮추기로 결정한 것은 아니다. 더 엄격한 전체 후보를 선택하려면 정상 이용 허용률을 다시 검토한다.
