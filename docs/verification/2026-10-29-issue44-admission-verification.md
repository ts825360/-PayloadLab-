# #44 2단계 — 정책 주입형 요청 입장 제한 모듈 검증

2026-10-29 / 이수웅(dtd2428), AI 보조. 상태: 모듈 구현·자동 검사 완료, 실제 앱 연결·정책값 승인 전.

## 이번에 한 일과 적용 범위

[admission.py](../../backend/app/core/admission.py)에 요청을 처리할지 결정하는 모듈을 추가했다. **main.app·review_app·라우트·Compose·프론트에는 아직 연결하지 않았다.** 따라서 현재 기본 서버가 요청량을 제한한다고 설명하지 않는다.

- Rate: 순간 허용량과 초당 보충량을 외부에서 받는다. 제품 기본 숫자는 없다.
- AdmissionPolicy: 전체/API 분류/선택적 peer 정책, 전체·분류별 동시 실행 상한, 최대 peer 수를 외부에서 받는다. 입력 map은 복사·읽기 전용화한다.
- AdmissionController.acquire: 잠금 안에서 필요한 예산과 빈자리를 모두 확인한 뒤 원자적으로 차감한다. 거부된 요청이 일부 예산을 쓰지 않게 했다.
- 임시 queue 정책: **대기열0, 즉시 거부**. 수업에 맞는 최종 운영 정책은 아직 미승인이다.
- _Lease.release: 슬롯 반납을 멱등 처리한다. 두 번 반납해도 카운터가 음수가 되지 않는다.
- AdmissionController.run: 허용한 async 작업을 내부 task가 소유하고 실제 완료 콜백에서 슬롯을 반납한다. 호출자 취소를 작업 종료로 간주하지 않는다.
- wait_idle: 소유한 작업의 정상 종료를 기다리는 drain 기능. 시간만 지나면 작업이 종료됐다고 처리하는 기능은 없다.

## 시험 숫자는 왜 이 값인가

시험값은 **경계 조건을 작게 드러내기 위한 값**이며 서비스 상한 후보가 아니다.

- 전체 허용량3: 3회 허용·4회 거부를 확인.
- 전체 허용량2와 분류별1: 거부된 분석이 다른 분류의 남은 예산을 소비하지 않는지 확인.
- 전체 동시 실행2·경쟁자8: 작은 통제된 스레드 경쟁에서2개만 입장하고6개 거부하는지 확인.
- peer 최대2·서로 다른3개 주소: 상태 개수가2개를 넘지 않고 이전 소진 예산도 보존되는지 확인.
- 보충률0.25: 빈도 초과 시4초 기다려야 함을 분명하게 드러내 재시도 시간 계산을 검증.
- 가짜 시계0.999/1/1.001초: 실제 기다리지 않고 보충 경계 직전·같음·초과를 확인.

이 숫자를 “모두가 사용한다”거나 프로젝트 운영 정책으로 제시하지 않는다. 실제 정상 학습 수요·환경 비용·대기 목표와 여유 정책을 근거로 다음 단계에서 제안해야 한다.

## 남은 일과 잘못 해석하면 안 되는 점

- 이 모듈은 **프록시 신뢰를 해결하지 않는다**. acquire에 넘기는 peer는 서버/운영 경계에서 검증한 값이어야 하며 XFF/Forwarded를 그대로 전달하면 안 된다. 이전 Uvicorn IP 재해석 발견도 그대로 남아 있다.
- 요청 분류는 caller가 전달한다. 실제 root/mount·직접 API·render 경로 매핑은 다음 연결 단계에서 검사해야 한다.
- run의 취소 검사는 모듈과 통제 worker의 경계다. 실제 HTTP 연결 해제·본문 수신·전체 timeout과의 동작을 아직 입증하지 않았다.
- slots는 소유한 awaitable의 실제 종료를 기준으로 한다. handler 자체가 별도 작업을 생성하고 기다리지 않는 경우나 강제 event-loop 종료·프로세스 중단은 보장하지 않는다.
- 무제한 대기를 만들지 않았지만 단일 프로세스/임시0대기열 선택이 모든 수업에 적합하다는 뜻은 아니다.
- 서버 전체 다중 worker 집계, 공개 원본 포트 접근 차단, 운영 경보·긴급 중지·학교 NAT 검증은 미완료다.
- API 응답과 프론트 재시도 안내, 실제 HTTP 집중·회복 검사는44-03에서 진행한다.
- #6/#24 정책 검토, 게시용 시작 댓글, 사용자 문서 검토, 커밋·푸시·PR·main 반영·이슈 종료는 하지 않았다.
