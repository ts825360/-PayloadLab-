# #42 상한 재산정 근거 — 2026-10-28

## 결론과 상태

수치를 관행으로 결정하지 않고 프로젝트의 보존할 입력 계약, 학습 자료, 실제 처리 비용과 명시적 서비스 예산으로 나눠 재산정했다. 아래 값은 팀 검토용 제안이며 제품 정책 미적용이다. 수학적으로 유일한 정답이나 운영 안전 보증이 아니다. 여유 배수와 시간 배분은 측정 사실과 구분한 정책 제안이다.

## 재현 범위

- main `64c9cb141108cafa5c6d215fc9eb4981c100b9b7`, #19 PR head `714a7412f6d638a297de33a07e37ff6f2027e720`를 각각 별도 임시 폴더의 backend/app으로 로드했다. 두 버전의 결과를 섞어 main 구현이라고 주장하지 않는다.
- 실제 저장소 제품 파일 수정 없이, 추적된 테스트의 literal dict 입력·frontend getLesson의 실제 제안 입력·#19 사례 JSON을 추출했다. 실행 가능한 테스트 전체를 재실행한 것은 아니다. 변수/동적 생성/fixture로 만든 입력은 추출 범위 밖이다.
- 별도 합성 사례: 2,000자 ASCII/한글/이모지/이스케이프 문자/script, 허용 history40개, 2,000자 이내 장문 및 짧은 UNION ALL 조합. 문자 크기 시험은 잘못된 입력도 모형의 unsupported 응답으로 정상 처리하는지 포함한다.
- route 함수 직접 호출과 JSON 직렬화 크기 측정이다. HTTP 본문 수신·Content-Length/청크·브라우저·동시성 시험이 아니다. XSS HTML은 브라우저로 열지 않았고 SSRF/CMDi도 모형만 호출했다.
- 실행기 측정에는 시험용100,000 VM/50ms 중단장치를 추가했다. 한계 도달 사례는 없었다. 조회별 정확 VM 수는 callback 간격1, route별 총 VM 수는 연결별100 미만의 오차를 위로 더한 상계다. SQLite 라이브러리 버전에 따라 VM 수가 달라진다.
- [재현 스크립트](scripts/issue42_measure_limits.py), [원자료](evidence/2026-10-28-issue42-sizing.json), [산정 요약](evidence/2026-10-28-issue42-sizing-summary.json).

### 보장 범위와 구현 주의

- 위의 8배/2배 여유, SQL 시간25% 배분은 팀이 승인할 정책 선택이다. 측정 결과가 그 배수를 자동 증명하지는 않는다. 각 선택이 허용/거부하는 수업 범위를 함께 검토한다.
- 실측 시간은 JSON 원자료에 보존했다. 한 Windows 기기의 동기 함수 호출만으로 공용 서버의 p95/p99나 처리 용량을 추정하지 않는다. 80ms를 코드에 넣기 전 목표 운영 환경에서 같은 수업 사례를 재측정해야 한다.
- progress_handler는 주기적 VM 점검이다. 느린 단일 함수, SQL 준비 단계, 직렬화 전체의 엄격한 벽시계/메모리 상한을 이것만으로 보장하지 않는다. 작은 중단 시험은 기법 검증이며 서비스 보호 전체 완료가 아니다.
- `SQLITE_LIMIT_LENGTH`는 문자열/BLOB뿐 아니라 내부적으로 인코딩된 행에도 영향을 준다. 셀8192를 그대로 이 설정에 대입해3컬럼 행을 깨뜨리지 않는다. 엔진 행/값 할당 경계와 fetch 후 셀·결과 직렬화 검사를 구분해 시험해야 한다.
- 문자 상한은 SQL 문장 전체 길이가 아니다. prefix/suffix, UTF-8 인코딩, EXPLAIN 접두사를 더한 엔진 SQL byte 길이는 별도 계산한다. 반환행 제한128은 EXPLAIN bytecode행에 그대로 적용하지 않는다.
- raw payload를 잘라 실행하지 않는다. 자원 제한 상태는 SQL 문법 오류/일반 이름 조건 불충족과 구분하며, traceback/내부 경로를 응답에 노출하지 않는다.

## 다음 검증과 미완료

1. 팀은 여유 배수·시간 배분과 허용 연산/함수 목록을 #6/#24에 기록한다. 숫자 산정만으로 authorizer 정책이 결정된 것은 아니다.
2. 결정 후 라우트 필드/전체 본문 수신 검증, 공통 SQL 예산을 단계적으로 구현한다. N-1/N/N+1 HTTP 시험과 SQL 행/셀/결과 상한을 실제 적용한 시험은 아직 하지 않았다.
3. 기존 SQL/Lens/Normal 회귀, 제한 초과 후 연결 정리·다음 정상 요청, 목표환경 시간 측정을 남긴다. 현재 자료는 모든 입력 호환성·보안/부하 검증 통과가 아니다.
4. #19 PR에 섞지 않았다. 이번에는 측정 스크립트·원자료·문서만 미커밋으로 작성했다. 제품 코드·공개 설정 변경 없음.

공식 기법 근거: [Python sqlite3](https://docs.python.org/3.13/library/sqlite3.html)의 set_progress_handler/setlimit 및 context manager 설명. 공식 문서는 프로젝트 제한 숫자를 정해주지 않으며 위 숫자는 우리 입력 계약·실측·서비스 목표에서 산정했다.

## 착수 후 교정

SSRF의 실제 입력 필드는 `target_url`이다. 초기 측정 도구의 `url` 별칭을 교정하고 고정된 두 SHA로 전체를 재측정했다. 현재 수치/원자료는 교정 후 결과이며 제안 상한값에는 변화가 없다. 제품 코드는 변경하지 않았다.

## 새 VM 집계 방식 호환성 재측정

짧은 문장 선차감 방식 보완 후 [SQL60사례 재대조](2026-10-28-issue42-sql-compatibility.md)에서 동일 요청의 resolve/trace/추가비교 최대1472단위, 별도 분석 요청320단위였다. 기존800 VM 상계와 새 보수적 집계는 서로 다른 측정이다. 현재8192제안 내 수업 사례가 들어감을 확인했으며 모든 SQL/운영환경을 입증한 것은 아니다.

## EXPLAIN 집계 보정

[EXPLAIN2차검증](2026-10-28-issue42-compile-second-verification.md) 후 분석 최대730, 시도1472로 갱신했다. 구현의8192단위는 VM구간·준비 여유·분석 목록 읽기를 포함한 보수적 작업 예산으로, 최초 VM명령8192 제안과 의미 차이를 팀 검토해야 한다.
