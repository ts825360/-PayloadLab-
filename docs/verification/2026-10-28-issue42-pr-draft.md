## PR 본문

기존 API는 화면의 입력 제한을 우회할 수 있고 실제 SQLite 조회의 계산량·결과량을 공통으로 제한하지 않았습니다. 명시적 정책을 주입하는 검토 앱에서 입력→SQL→응답을 제한하고, 초과 상태를 문법 오류·조건 불충족·공격 성공과 구분하도록 구현했습니다.

### 변경

- 필드 타입·2000자·본문32KiB·history40개/총2000자 검사. 실제 청크 bytes·중복JSON키·비정상 인코딩·render 입력도 실행 전에 확인.
- 요청별 공유 SQL 작업/시간 예산, 허용 연산 검사,128행·셀8192bytes·SQL결과32KiB 한도와 모든 경로 연결 정리. resolve/trace/EXPLAIN/상수비교를 연결하고 제한 후 부분 성공을 제거.
- 응답256KiB 상한에서 헤더/부분 데이터를 보내지 않고 중단 안내. 스트림 완료/연결 종료/중복 시작도 확인.
- /api 등 mount 접두사에서도 입력·SQL·응답 제한 유지. 병렬 요청의 예산/실패 상태 분리.
- 자원 제한·연산 차단을 테이블 없는 안내로 렌더. API413/422/response_limit503의 안전한 문구를 실행/자동분석 화면까지 전달하고 다음 정상 요청 복구.

### 중요한 적용 상태

**app.main.app의 기본 정책은 비활성입니다.** 검토 앱과 명시적 로컬 실행기로만 정책을 주입했습니다. 이 PR을 병합했다고 기본 서비스가 보호됐거나 #42가 완료됐다고 간주하면 안 됩니다.

숫자·SQL 허용 목록은 #6/#24 팀 검토 대기입니다. 초기 VM명령 제안과 달리 구현8192는 progress구간+문장여유+EXPLAIN목록을 합친 보수적 작업단위입니다. 의미와 여유를 검토해야 합니다.80ms는 주기적 점검 목표로 엄격한 OS시간/메모리 보장이 아닙니다. 시험용 함수목록(length/printf/sum)을 과목의 최종 허용목록으로 확정하지 않았습니다.
