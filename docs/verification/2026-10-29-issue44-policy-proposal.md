# #44 정책 후보 — 프로젝트 근거와 인원별 비교안

> 2026-10-29 / 이수웅(dtd2428), AI 보조 / **사용자 검토용 로컬 초안**
>
> 최종 동시 학습 인원과 정책값은 태성님이 결정한다. N은 미선택이다. 아래1/4/8/16은 비교 행이며 운영 최대 인원·팀 인원으로 확정한 값이 아니다. 제품 기본값·기본 앱·Compose를 변경하지 않았다.

## 1. 문제: 무엇을 결정해야 하나

#44 모듈·검토 앱 연결·취소 정리는 구현했고, 직전 backend433개가 통과했다. 하지만 시험용2·3 같은 숫자는 서비스 정책이 아니다. 실제 학습의 요청 수요, 처리 비용, 같은 IP 사용자, worker/프록시 조건을 근거로 빈도·동시 실행·대기열·시간을 검토해야 한다.

이번 목적은 “왜 이 상한인가?”를 설명하는 후보식을 만들고 태성님이 선택할 조건을 드러내는 것이다. 값을 정했다는 이유만으로 #44나 공개 전 보안 검토를 완료하지 않는다.

## 2. 의도: 지키려는 학습 동작과 가정

- 한 학습 작업공간에서 자동 analyze와 수동 attempt가 겹칠 수 있다.
- XSS는 attempt 결과 후 render를 여는 별도 요청이 있다. 처음에는 labs 목록도 가져온다.
- 자동 분석만 몰려 수동 작업의 자리를 전부 차지하지 않게 분류별 동시 실행을 제한한다.
- 학교 NAT처럼 IP 하나에 여러 작업공간이 있을 수 있다. IP를 인증 사용자로 해석하지 않는다.
- N은 “선택한 동시 학습 작업공간 수”다. 사람 한 명이 여러 탭을 쓰면 그 수요도 포함해야 한다.
- 현재 인증이 없으므로 N별 후보는 **서비스·API 분류의 합계**다. 사람별4회 제한을 실제로 식별·보장한다는 뜻은 아니다. 요청 헤더로 N이나 사용자 예산을 늘릴 수 있게 하지 않는다.

수동 실행·미리보기에 자동분석과 같은 조작 주기를 허용하는 것은 아래에서 밝히는 정책 선택이다. 실제 사람이 매320ms마다 모든 동작을 한다고 관찰한 것은 아니다.

4N burst가 동시에4N개를 실행한다는 뜻은 아니다. 선택할 동시 실행 A2N/B3N과 별도다. 모형은 metadata 후 분석+실행, 실행 응답 뒤 render 순서다. 추가 탭·겹친 미리보기·느린 본문은 이 가정과 다를 수 있다.

또한 분류별N·전체 A2N/B3N은 완전한 공정 스케줄러나 개인별 예약을 제공하지 않는다. 다른 분류가 자리를 점유하면 정상 요청도503을 받을 수 있다. 익명 공격자에게도 공유 예산이므로, N명의 정상 사용자를 공격 중 항상 보장한다는 뜻은 아니다.

320ms 목표는 입력을 멈춘 뒤 이미 기다리는320ms debounce와 별개다. 입력부터 화면 표시까지320ms로 보장하지 않는다.

### 2차 검증에서 보완한 동시 실행 가정

기존 A안2N은 관측 보유시간133ms의 가상 재생에서는 통과했다. 그러나 각 응답161ms에서도 이전 render가 다음 analyze/attempt와 겹치면 거부가 발생했다. N=1·10회 조작 모형에서 시도5건이503에 해당하는 concurrency_limit으로 거부됐다. 각 응답이320ms 목표 이내라는 사실만으로 A안을 정당화할 수 없다.

B안3N을 비교 대안으로 추가했다. 같은 정수ms 시간 모형에서 응답133/160/161/200/320ms는 거부 없이 통과했고321ms에서는 분류 상한으로 거부됐다. metadata는 시작 때 완료된 뒤 학습한다는 모형이며, 네 분류 동시 실행·임의 탭·실제 운영을 모두 보장한 것은 아니다.

이는 가상 모형 비교다. 실제 동시 측정은 여전히1/2/4/8뿐이다. 특히 N=4의 B안은12동시라 현재 실측으로 검증되지 않았다. A/B 어느 쪽도 최종 선택하지 않는다. [2차 검증 상세](2026-10-29-issue44-policy-second-verification.md).

또한 초당13N·burst4N은 분류별 상한의 합계와 같아 더 엄격한 독립 서비스 상한은 아니다. 후보가 명시하는 합계 경계와, 전체 상한 모듈이 독립적으로 작동한다는 검증을 구분한다. 더 낮은 전체 상한이 필요하면 정상 흐름·거절 비율을 다시 검토해야 한다.

### 인원별 비교 — 어느 인원도 선택하지 않음

CPU 계획값=초당 전체 요청수×8.961ms. 서로 다른 환경·더 무거운 입력에서는 달라진다. “1CPU의50% 안에서 우선 검토”는 변동/GC/미측정 비용의 여유를 남기려는 **팀 검토용 정책 선택**이며 측정이 자동 증명한 안전 계수가 아니다.

## 6. 검증: 후보식이 모형 안에서 무엇을 만족했나

- 기존 A안2N에서 N=1/4/8/16 각각 현재27단계+선택 render를 같은 IP/다른 IP로 재생하고, 매 단계 render를 여는 합성 모형도 실행: 총12시나리오.
- 가상 입장5,858건은 모두 허용되고 최종 슬롯0·peer 추적0. 이 수를 HTTP816건이나 pytest433개에 합산하지 않는다.
- 보유시간은 관측 최대132.51ms를 올린133ms. 단계 간320ms, render는 실행 응답 뒤 발생하는 가정이다. 두 응답266ms가320ms 안에 들어가는 현재 표본에서의 결과다.
- 기존 A안 재생은 초기4N 예산 뒤 거부, 2N 실행 중 거부, 반납 후 회복을 확인했다. 초기4N은 전체와 분류 예산이 함께 소진되므로 이 검사 하나로 전체 예산만의 효과를 입증하지 않는다. 후속 독립 대조4건에서 분류 예산은 그대로 두고 전체 burst만 바꿔 거부/허용 차이를 확인했다.
- 위133ms의 A안 모형에서는 N=8/16도 통과한다. **가상 슬롯/토큰 모형이 통과한 것과 실제 용량이 맞는 것은 다르다.** 위 표의 운영 보류 조건을 지우지 않는다.
- 이번에는 제품 소스를 바꾸지 않았다. 기존 backend433개·프론트138개/빌드488을 새로 수행했다고 쓰지 않는다.

실행 코드 기준은 HEAD eaa3998526b60ea0109cd1b9a08914336944a806 + 기존 #44 미커밋 구현이다. 이번 측정·재생 스크립트와 입력/환경/해시는 [감사 근거](evidence/2026-10-29-issue44-policy-audit.json)에 연결한다.

## 7. 한계: 운영 전 무엇을 더 결정해야 하나

- 태성님이 N과 정상 사용 범위(탭/공동IP/동시 조작)를 결정해야 한다. 인원/후보값은 아직 승인되지 않았다.
- 목표 Python3.12·1CPU/256m·실제 프록시·네트워크에서 같은 정책을 켠 재측정이 필요하다. 이번은 Windows8논리CPU 환경이다.
- 앱 대기열0은 TCP 대기열/서버 버퍼가0이라는 뜻이 아니다. 설치 Uvicorn 검토 설정의 backlog2048은 연결 대기 설정이다.
- 현재 검토 설정의 keepalive5초는 유휴 연결 설정이며 본문 수신/전체 작업 timeout이 아니다. graceful shutdown timeout은 미설정이다. [실제 설정 기록](evidence/2026-10-29-issue44-policy-server-settings.json).
- 실제 수신/전체 timeout·강제 종료·느린 연결·강한 입력 혼합·과부하 경보·긴급 중지를 검증해야 한다. 취소 정리는 작업 강제 중단을 대신하지 않는다.
- 단일 worker/인스턴스만 현재 메모리 합계를 공유한다. worker가 늘면 공유 저장소의 원자 집계 또는 검증한 공통 gateway가 필요하다. 프로세스별 숫자를 단순히 서비스 전체 한도라고 쓰지 않는다.
- 로컬은 proxy_headers=False로 임의 IP 헤더를 신뢰하지 않는다. 공개 시 신뢰 peer/프록시 목록·헤더 덮어쓰기·원본 API 접근 차단은 #12/#24의 실제 운영 경계에서 결정/시험한다. '*' 전체 신뢰를 기본 제안하지 않는다.
- health/docs/OpenAPI·CORS preflight는 현재 labs 카운터 밖이다. 엣지 보호/노출/별도 상한은 운영안에서 확인해야 한다.
- 새 로그인·익명 식별자·Redis·공개 서버·외부 부하 시험을 추가하지 않았다.
- 자동분석 cooldown·초기 목록의 상세 재시도 안내·실제 브라우저/학교 NAT 이용자 검증은 별도다.
