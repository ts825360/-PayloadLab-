## 실제 수행한 작은 시험

[스크립트](scripts/issue44_discovery.py) / [원자료](evidence/2026-10-29-issue44-discovery.json).

- OS·Python·uvicorn/fastapi/starlette/anyio 버전·소스 해시·요청 입력·상태·바이트·요청별 경과 시간을 JSON에 저장했다.
- 제품 app을 메모리 wrapper로 감싼 임시 loopback 서버만 사용. 진단 endpoint는 wrapper에만 존재하며 제품 API에 추가하지 않았다.
- 실습 13개 × analyze/attempt =26경로, XSS render 2경로, health/목록 2경로: **30경로 × 3회 =90건**, 모두200.
- /api mount 뒤 SQL analyze 3회: 모두200.
- 프록시 설정3종 × root/mount 2종 × 헤더4종 =24건: 모두 예상한 peer IP 관찰.
- 총 **117건, 순차 실행**. 동시 실행·burst·용량 시험이나 제한 장치가 작동한 시험이 아니다. 관찰한 117건을 117개 pytest 검사로 세지 않는다.
- 생성한 서버는 종료하고 thread 종료를 확인한다. 원래 개발 서버/컨테이너는 변경하지 않는다.

| 명시적 시험 설정 | 헤더 | 앱에 보이는 IP | 의미 |
| --- | --- | --- | --- |
| proxy_headers=True, trusted=127.0.0.1 | 없음 | 127.0.0.1 | 실제 loopback peer 유지 |
| 같은 설정 | X-Forwarded-For:198.51.100.10 또는 .11 | 해당 헤더 값 | 앱에 오기 전에 Uvicorn이 peer를 바꿈 |
| 같은 설정 | Forwarded만 전송 | 127.0.0.1 | 시험한 Uvicorn0.32.0에서는 이 헤더로 peer를 바꾸지 않음 |
| proxy_headers=False | 위 모든 헤더 | 127.0.0.1 | 앞단 헤더 변환을 사용하지 않는 경계 확인 |
| proxy_headers=True, trusted=192.0.2.10 | 위 모든 헤더 | 127.0.0.1 | 연결한 loopback이 신뢰 대상이 아니므로 XFF 무시 |

이것은 **로컬 loopback 신뢰 설정**의 재현이다. Docker NAT·실제 CDN/프록시·공개 환경에서 같은 peer로 보인다는 증거는 아니다. 198.51.100.x와192.0.2.x는 헤더/설정의 통제된 예시이며 외부로 접속하지 않았다.

스크립트는 이 환경의 Uvicorn 기본 proxy_headers·forwarded_allow_ips·workers·limit_concurrency도 별도 기록한다. 환경변수의 영향을 받을 수 있으므로 시험 profile 설정과 환경 기본값을 혼동하지 않는다.

## 프로젝트별 정책 산정 방법 — 아직 숫자 확정 없음

### 자동 분석 빈도

320ms는 debounce 대기이므로 지속 입력이 멈춰야 요청이 발생한다. 25번 변경의 timer 모형에서 100ms 간격이면1회, 400ms 간격이면25회가 발생했다. 이는 단순 timer 계산이며 실제 React/사람의 사용 측정은 아니다.

한 탭에서 320ms보다 조금 긴 간격으로 반복 변경하면 이상적으로 초당 약3.125회 분석 수요가 생길 수 있다. 이 값은 서버 상한이 아니라 **현재 UI의 분석 수요를 검토할 기준**이다. 직접 API와 여러 탭은 이 간격을 지킬 이유가 없다.

### 전체·API·IP 상한 구분

- 자동 분석과 수동 실행·render의 요청 예산을 구분하되 전체 합계도 제한하는 구조를 시험한다. 자동 분석이 실행 예산을 다 소모하는 일을 피하기 위해서다.
- 수치 제안에는 정상 동시 학습자 수 N, 각 유형 요청 패턴, 허용 응답 지연, 처리시간/CPU/메모리 관찰, 여유 정책을 함께 적는다.
- N=4는 개발팀 인원이지 운영 수용 인원 확정값이 아니다. 4명이라는 대화만으로 전체/IP 상한을 고정하지 않는다.
- 학교 NAT는 여러 정상 사용자가 같은 IP일 수 있으므로 IP를 사용자 인증처럼 사용하지 않는다. 인증/세션이 없는 현재 프로젝트에 새 로그인을 임의로 만들지 않는다.
- IP별 상한만 두면 식별자 변경으로 총량이 커진다. 전체 집계는 IP·랩·경로가 바뀌어도 공유되어야 한다.
- 현 단계에서는 세 요청의 경과 시간으로 p95·처리 용량·공용 서버 상한을 추정하지 않는다.

### 동시 실행·대기열·시간

입구에서 허용한 요청 수와 실제 동기 worker 작업 수를 연결해야 한다. 요청 timeout/브라우저 abort 뒤 응답만 끝내고 실행 슬롯을 돌려주면 실제 작업이 남을 수 있다. threadpool 동기 함수의 취소/종료를 통제된 event 기반 시험으로 확인한 뒤 방식을 정한다.

무제한 대기열을 만들지 않는다. 대기열0 즉시 거부와 유한 대기열을 시험 대상으로 비교한다. 시간값은 #42 SQL 협력 중단과 HTTP 수신/대기/전체 실행 시간을 구분한다. 새 프로세스 격리나 라이브러리를 임의 도입하지 않는다.

### 프록시·worker 운영안

- 로컬 직접 API는 앞단의 자동 IP 재해석을 끈 시험 경계를 우선 검토한다. 실제 제품 설정은 아직 변경하지 않았다.
- 운영은 신뢰할 연결 peer/프록시 목록과 헤더 덮어쓰기·정규화 주체를 정한다. 임의 XFF/Forwarded를 바로 제한 키로 사용하거나 '*' 전체 신뢰를 기본값으로 두지 않는다.
- 원본 API는 운영 네트워크에서 신뢰 프록시만 접근하도록 하는 책임·설정을 #12/#24와 연결한다. 앱 카운터만으로 방화벽/도메인/포트 우회 차단 완료를 주장하지 않는다.
- 메모리 카운터는 프로세스마다 분리된다. 다중 worker의 서비스 전체 제한으로 제시하지 않는다. 최초 검토는 단일 프로세스의 범위를 명시하고, 다중 worker/인스턴스는 공유 저장소 원자 집계 또는 검증한 공통 gateway가 필요하다.
- 키를 늘려 메모리를 소비하는 경우를 고려해 카운터 최대 개수·보관/삭제·한도 시 거부 방식도 시험한다. #45 보관 정책과 연결한다.
