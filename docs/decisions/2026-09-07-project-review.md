# PayloadLab 기획안 평가와 보완 기록

연결 이슈: [#2 기획·범위·발표 자료 허브](https://github.com/ts825360/-PayloadLab-/issues/2), [#3 작업 흐름](https://github.com/ts825360/-PayloadLab-/issues/3)

평가자: Codex (기획 검토 역할)

## 한 줄 평가

**보안 입문자가 “정답을 맞히는 경험”보다 “왜 되는지 이해하는 경험”을 하게 하려는 방향은 분명하다.** 다만 현재 문서는 초보 팀원에게 어려운 표현이 많고, 첫 버전과 확장 기능의 경계가 더 선명해야 한다.

## 잘한 점

| 항목 | 평가 | 이유 |
| --- | --- | --- |
| 문제의식 | 좋음 | 설치 장벽과 복습 부족이라는 실제 입문자 문제를 잡았다. |
| 차별점 | 좋음 | 정적인 소스 보기보다, 사용자의 입력이 실제 교육용 흐름에 어떻게 들어가는지 보여 주려 한다. |
| 학습 방식 | 좋음 | 실패를 오답으로 끝내지 않고 Lens를 통해 다음 시도를 만들게 한다. |
| 안전 방향 | 좋음 | 외부 대상 공격과 임의 명령 실행을 범위에서 제외했다. |

## 보완이 필요한 점

| 항목 | 현재 문제 | 이번에 반영한 수정 | 다음 결정 |
| --- | --- | --- | --- |
| 읽기 쉬움 | 일부 이슈가 기술 용어와 긴 배경 설명으로 시작했다. | 한 페이지 기획안과 쉬운 이슈 형식으로 바꾼다. | 팀원이 읽어 보고 어려운 문장을 계속 고친다. |
| 범위 | SQL·XSS·IDOR와 SSRF·리눅스 계획이 한 덩어리처럼 보였다. | 첫 버전 중심과 확장 후보를 분리했다. | #5에서 확장 시작 조건과 담당자를 결정한다. |
| 성공 기준 | “좋은 학습 경험”을 어떻게 확인할지 정해져 있지 않다. | 평가 항목으로 남겼다. | 입문자 2~3명이 Lens 설명만 보고 다음 입력을 만들 수 있는지 확인하는 간단한 사용성 점검을 설계한다. |
| 안전 표현 | “위험이 없다”라고 단정하면 실제 구현과 어긋날 수 있다. | “교육용 범위로 제한하고 공개 전 점검한다”로 유지했다. | #6과 #24에서 기능별 제한과 공개 조건을 정한다. |
| 팀 협업 | 기존 기록이 답처럼 보일 수 있었다. | 모든 기록을 열어 두고 재검토 원칙을 추가했다. | 담당자는 대안과 근거를 댓글 또는 `docs/`에 남긴다. |

## 현재 추천 우선순위

1. #5에서 첫 버전의 범위를 확정한다.
2. #7, #10, #11로 “입력 → Lens → 그림 → 재시도” 흐름을 초보자가 이해할 수 있게 만든다.
3. #14~#16에서 SQL·XSS·IDOR의 설명 문장을 준비한다.
4. #6, #12, #24에서 안전 기준과 실행 환경을 확인한다.
5. 위 네 단계가 안정된 뒤 SSRF와 리눅스 퀴즈를 다시 판단한다.

## 평가 결론

이 프로젝트는 “보안 지식을 많이 보여 주는 서비스”보다 “한 번의 입력을 이해하게 만드는 서비스”에 집중할 때 가장 설득력이 있다. 이후 기능을 추가할 때도, 초보자가 다음 시도를 스스로 만들 수 있는지부터 확인한다.
